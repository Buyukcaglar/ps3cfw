# HW002P native sparse probe review

HW002O's guarded capture succeeded after the initial access-denied output was preserved and a fresh elevated output was used. It captured 2,140,672 bytes through the bounded metadata cache; the saved snapshot is 2,174,120 bytes. Two mappings replay exactly, the label/metadata anchors match, clean flag is 1 and pending blocks zero. The two N payload ranges end below 48,776,777,728 bytes; bytes above the original 1536 GiB gate are zero. These are metadata-derived locations, not new payload reads or whole integrity proof.

## Native allocator evidence

The supplied kernel ELF contains a 64-bit UFS2 block-preference function at VA 0x80000000001f132c..0x80000000001f153f. Its 532 bytes hash to 33abd5cc6ff731e6f882bc1d06e1e4bfc5fb9dc71580c019508879e337e4d06e. The `observations/HW002P/native-preference.txt` artifact preserves its full disassembly. Ten direct call sites were found in the supplied ELF; an allocation caller at 0x1f6760 passes a logical block, pointer index and inode data-pointer array. This is supplied-image static evidence; the function has not been traced executing on this PS3.

The function loads fs_maxbpg at +0x5c, fs_ipg at +0xb8, fs_fpg at +0xbc and fs_ncg at +0x2c. Current captured values are 2048, 36992, 73900 and 6602. It uses the inode number at +0x40 and inode filesystem pointer at +0x50. For a new section with a zero previous pointer and a sufficiently large logical block, its preferred group starts from `(inode_group + logical_block / fs_maxbpg) % fs_ncg`, then scans for at-least-average free blocks. The native summary lookup explicitly switches arrays for groups above 4095. High addresses therefore need direct qualification of that actual path as well.

This shape is consistent with the historical upstream [FreeBSD 5.4 UFS allocation source](https://raw.githubusercontent.com/freebsd/freebsd-src/releng/5.4/sys/ufs/ffs/ffs_alloc.c). Upstream describes inode-local allocation for early blocks and free-block-aware group selection for later sections. It is a reference for investigation, not proof that Sony's implementation is equivalent. The placement prediction here uses the supplied PPC instructions and captured geometry, rather than assuming upstream behavior.

`tools/Model-Ufs2BlockPreference.py` interprets this exact fixed function on synthetic memory. Cases cover low/high summary arrays, the direct/single-indirect boundary, previous-pointer continuation, unavailable groups and wraparound. With inode group 34 and lbn 13,242,368 (file byte offset 216,962,957,312), the model reaches group 6500 and returns preference fragment 480,350,004 when that group meets the average-free condition. A preference is not necessarily the exact allocated block. The unmodified native allocator still chooses actual free blocks. The model is not execution on hardware, and no kernel patch or live syscall probe is introduced.

## Native request and guard review

The existing pinned webMAN write endpoint uses a 64-bit offset, parsed with signed-64-bit decimal conversion, and ordinary CellFs open/seek/write/close. Its position-plus-hex-data path opens with O_CREAT|O_WRONLY and no truncation. The proposed request is under 512 characters and supplies exactly 64 binary bytes. This source behavior is not proof of full source/binary equivalence with the installed webMAN; actual size and data checks remain mandatory. The helper's missing seek/write/close status checks are unchanged. A failed seek could place data at offset zero, which the exact-size guard rejects on the new test file. Existing N/control paths are never write destinations.

The command exits through CODE_PREVIEW_FILE rather than streaming the target file. The pinned response helper builds a small preview/link page; this tool reads its bounded HTTP response without opening links or images. This avoids accidentally downloading or hashing the entire large sparse target. The source files for the command, decimal parser, file helper, FTP helper and HTTP preview are included in the binding manifest.

`tools/Run-HW002P-SparseNative.py` binds review/contract/readiness before network or output creation. Only the two fixed new filenames, offsets and payloads can enter its write socket. Absence is checked twice; this is not atomic exclusive creation, so the prerequisite includes idle file activity. Durable intents and consumed-write checks prevent retries within a phase; exclusive phase output prevents replay. There are no STOR/APPE/DELE/SITE/MKD commands, redirects, raw disk access, memory writes, firmware access, repair, cleanup or automatic rollback. Large sparse full hashing is excluded from the endpoint allowlist. The after-boot phase rejects write requests explicitly.

The 16 MiB sparse canary precedes the high-offset request. Its full native MD5 validates the complete zero gap plus fixed payload. Both targets require exact size and exact EOF tail containing the preceding 4096 zero bytes plus payload; cumulative free-space decrease must remain within 2 MiB. A failed canary or unknown native outcome stops before the high request. Full original N hashes and fixed complete control reads establish preservation within that scope. They do not qualify unrelated files or whole-filesystem integrity.

The separate sparse mapper visits only nonzero indirect subtrees, validates reviewed geometry and bounded metadata extents, rejects aliased metadata pointers, overlapping payload spans and more than 256 indirect blocks, and records holes explicitly. It neither opens a device nor reads keys or file payload. The fixed paths and 256 GiB logical-size bound prevent arbitrary traversal. Future raw capture requires separate fresh physical-move/identity custody and review; no such capture or native sparse write has happened yet.

## Validation and limits

`analysis/dev006/test_hw002p_sparse.py` passed 72 host checks: actual-instruction fixtures; direct/single/double/triple sparse trees; comparison with the frozen mapper; fixed payload and independent canary hash; HTTP/parser and FTP allowlists; exact/short/excess/corrupt tails; and isolated complete write/after-boot protocol simulations. Failure simulations cover missing readiness, existing destination, wrong size, wrong tail, excessive allocation, wrong canary hash and unknown response. Each stops before the high write. The success model performs exactly two writes and no after-boot writes. No disk, key or real network was accessed in these host tests.

The logical high file is approximately 202 GiB but intended actual data is only 64 bytes plus native metadata. Sparse behavior must be established by the canary before this operation. Triple-indirect native I/O and predicted high placement are both still hardware hypotheses. After native write/restart checks, a fresh read-only physical mapping must prove actual placement; full capacity, crash durability, populated repair, other SSDs, migration and >2 TiB remain pending. No firmware change is justified by this result alone. DEV006 and HW002L's unexplained allocated metadata remain open; no offline writer is released.
