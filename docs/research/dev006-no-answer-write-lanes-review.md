# Checker no-answer and write-descriptor review

13 October 2026. Exact original utility SHA-256 `6fdcb1ab4a25c29230dbd5fdf0f2594ee8c9c5187ee3c13dbd384128c2504b9a`. This is primary-agent static/model work. No checker execution, console write, new firmware build or populated repair occurred.

`analysis/dev006/checker-no-answer-v1/evidence.json` pins 56 captures. The no-answer byte is global `0x4c5b4`, reached through several TOC slots, including `0x26ec4` for the option handler and `0x27478` for setup. Seven explicit TOC references were found; that inventory is not a complete alias proof. The handler increments a byte and clears the yes flag. Repeating `-n` 256 times can wrap this byte to zero; any eventual controlled argument contract must admit one exact option, rather than arbitrary repeated options.

`analysis/dev006/checker-write-descriptor-v1/evidence.json` pins another 18 captures and 82 direct branch sites. Its provisional `write_descriptor_aliases` field included one incorrect proposed alias: slot `0x273ac` points to a different object. The accompanying interpretation errata supersedes that field. The confirmed setup and flush aliases are `0x27390` (TOC displacement `-0x7430`) and `0x26c88` (`-0x7b38`), both pointing to global `0x4c620`.

The setup function initializes that descriptor to -1 at `0x1f27c`. In the captured ordinary lane, a nonzero no-answer flag skips the write-open branch at `0x1f910`. The latter passes flag 1 to the open wrapper, which forwards it to syscall 801. The flush entry at `0x1558c` checks the same descriptor and branches away when negative; block writer `0x14918` also checks its supplied descriptor before seeking/writing. These are concrete guards for the reviewed lane, rather than proof that every checker path is read-only.

The answer routine at `0x14618` distinguishes the literal `CONTINUE`: a nonzero no-answer flag can still produce a yes answer for that question. Therefore a proof based only on every repair question returning no would be incorrect. Descriptor and side-effect analysis is necessary.

The actual-instruction model in `analysis/dev006/checker-write-lane-model-v2/result.json` passes 16 combinations of the captured setup flags/open results and four byte-counter cases. It confirms that the modeled lane calls the write-open wrapper only when the mounted-condition flag and no-answer flag are both zero. The first model attempt lacked a file-backed TOC load in its environment and stopped with a host KeyError; it ran no firmware or hardware. Its source and failure record are retained. V2 supplies reads from the pinned ELF for those immutable words. Callees remain abstractions, so these results do not establish kernel behavior or whole-checker safety.

The syscall inventory includes direct writes, raw storage writes, a positioned-write operation through syscall 817/fcntl, and unmount wrappers. Names/numbers are cross-checked against [RPCS3's primary syscall table](https://github.com/RPCS3/rpcs3/blob/master/rpcs3/Emu/Cell/lv2/lv2.cpp); emulator naming does not establish Sony-kernel side effects. Unmount caller contexts at `0x3120` and `0x3194` and alternate positioned-write caller `0x8f40` are captured, but their reachability and all argument/dirty-state behavior under a future checker invocation remain open.

No `-n` checker invocation is released. DEV006 still requires allocator/alias coverage, a defensible allocator-wide bound or high-water measurement, repair-context container headroom and failure behavior, and a verified restorable fixture before populated checker execution. The successful LBP3 game save/load is a separate ordinary-I/O observation. P8 remains unchanged; stable storage support remains false.
