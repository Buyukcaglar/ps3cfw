Public libfs read NID4d5ff8e2 at0x1154 calls802; write NIDecdcf2ab at0x11ac
calls803. Public sysFsGetFreeSize is more complex than raw840: its fast route
uses fcntl817 commandc0000002, with fallback840 and adjustment/division logic.
BF directly calls840 twice per1MiB, plus a post-open check. Do not silently
equate an SDK declaration, public wrapper or checker utility with the full
ordinary filesystem path. The installed78487B P13 utility readback is exact
for that file; it is not whole installed LV1/LV2 readback. Saved package lineage
and comparison ELF evidence support the mapped code, with that provenance limit.

The traced raw840 route reaches UFS2b1940..2b1a4c. That bounded body computes
from in-memory filesystem summary/reservation fields; it has no bitmap walk
or I/O call. Therefore 'a whole bitmap scan for every BF free-space query' is
contradicted in this path. Lookup/locking/syscall latency still costs time and
is unmeasured. Actual allocation is different: ffs_alloc1f3e00, group search
1f1540, alloccg1f4a4c/full-block1f3c0c and cluster1f4640 have group/bitmap and
metadata work. Its cost may vary with fragmentation/available blocks, but no
BF allocation trace or extent map attributes either32GiB/336GiB step to it.

LV1 contains48-bit DMA EXT read/write builders (0x25/0x35), selected using the
device's IDENTIFY-derived flag, plus IDENTIFY0xec, FLUSH CACHE0xe7/EXT0xea,
SMART0xb0, SET FEATURES0xef and STANDBY IMMEDIATE0xe0 builders/callers.
This contradicts a blanket absence of advanced commands. It does not prove
every function is reachable through ordinary OS requests or used at runtime.
Generic taskfile plumbing is not proof of a permitted end-to-end DSM route.
No complete filesystem discard caller/forwarding proof or native command trace
is available; mark PS3 TRIM forwarding/issuance/effect UNKNOWN. No explicit
filter/unsupported response or universal absence is inferred from a search.
Exact console link rate, effective device queue depth and NCQ/FUA use remain
unknown; synchronous BF application depth1 does not establish controller depth.

Durability must remain separate. Existing exact-kernel evidence distinguishes

Read versus write bottleneck assessment
======================================
Confirmed measurement limitations:1MiB serial guarded operations; scalar
pattern/SHA, extra comparison/regeneration on reads; two raw840 calls perMiB
write; absent STOP-file lookup perMiB; controller/callback work; time-based
UI rendering/flip;256MiB progress write/fsync and per-file sync/close. See
diagnostic-cost-audit.json for exact source locators/counts. Buffers are128B
aligned in BF, not proven4KiB pointers; logical sizes/offsets are4KiB multiples.
No kernel bounce-buffer/copy/crypto time or physical read-modify-write is measured.

Reads:14.84MB/s verified-read may be a CPU/copy/UI ceiling. Syscall-only reads,
small/random latency, game-asset streaming and metadata/open costs are unknown.
Flat verified reads cannot exclude slower media hidden below that ceiling.

Writes: fixed per-byte pattern/hash work cannot by itself explain a new step
unless its native timing changes. Allocation/metadata/cache contention, variable
guard/USB/UI time and SSD GC/cache/temperature/history remain candidates.
Time-based UI work perMiB can grow as the loop slows. No evidence ranks SSD GC
above allocator/driver causes or proves thermal throttling/cache exhaustion.
Pure write bandwidth, syscall tails and sync/close completion remain unmeasured.

Ordinary games do not run BF's reserve/STOP/pattern loop; a faster diagnostic
does not imply faster games. Installs emphasize creation/allocation/metadata and
sustained writes. Saves emphasize short writes, ordered sync/close and latency
tails. Streaming emphasizes locality, small/random reads and memory scheduling.
Each needs its own comparable workload before a practical improvement claim.
