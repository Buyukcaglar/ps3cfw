# PERF001 analysis of the native read/write measurements (2026-10-29)

native results that were never copied back into `docs/research/PERF001/`, and
interprets them. All numbers can be re-derived with `python tools/perf_summary.py`
(read-only, from the archive). MB/s is decimal (10^6 B/s); GiB is binary.

BF has no per-call timing. Its write-call rates are inferred by subtracting BH's constant

## Interpretation

1. **The old "read ~14 MB/s" figure was the test app's CPU, not the disk.** On the PPU,
   pattern generation plus SHA-256 run at 14.4 MB/s (7.5 s + 8.2 s per 256 MiB). Reads inside
   the filesystem calls ran at ~59-61 MB/s in every test.
2. **Reads are capped at ~60 MB/s by the console's storage stack, not by the SSD or the disk
   position.** The rate is identical early, middle and late on the disk, for game files and for
   filler. A SATA SSD reads several times faster even on a 1.5 Gb/s link. The latencies fit
   a fixed cost of roughly 0.7-1 ms per device request plus about 64 KiB per request:
   * a 64 KiB read takes 1.28 ms, and 4 KiB takes 0.77 ms;
   * a 1 MiB read takes 17 ms, which matches about 16 serial 64 KiB pieces;
   * 64 KiB random reads (66 MB/s) are no slower than 1 MiB sequential ones.

   This 64 KiB chunking is a hypothesis; no request sizes between 64 KiB and 1 MiB were measured.
   Either way, the limit sits in LV2/LV1 storage handling, which the project does not patch.
3. **Write slowdowns originate below the filesystem.**
   * At 93-94 % filesystem fill (BH start), write calls ran at 28.7 MB/s, the same as BF
     at ~50 % fill. The UFS allocator is therefore not the bottleneck, at least up to 94 % fill.
   * In both fills the first cliff came after 26-28 GiB of writing, at 923 GiB free in BF and
     at 106 GiB free in BH. It depends on bytes written, not on free space.
   * The fast regime returned after roughly 4 hours without writes between BF and BH.
     The ~20-minute read-back pauses neither prevented nor reversed the cliff.

   This fits an SSD write cache (pseudo-SLC) of ~26 GiB that drains when idle. Thermal
   throttling would also fit: both cliffs came about 1.05 h into a run, so this data cannot
   separate the two.
4. **The sustained floor depends on the SSD's internal state.** After the cliff, BF wrote at
   ~22 MB/s (inferred), and only after 336 GiB dropped to the ~12 MB/s floor that BH hit
   at once. The best fit is that the SSD ran out of never-written (clean) blocks and now has to
   garbage-collect while writing. The PS3 most likely never sends TRIM: the static analysis
   found no DSM/TRIM command builder in LV1, and `findings.txt` rates TRIM issuance unknown.
   Without TRIM, deleted data still occupies blocks inside the SSD.
5. **Even the fast write regime costs twice as much as a read (36.5 vs 17 ms/MiB).** The PS3
   side (write cache policy, flushes, metadata, encryption) is the likely cause. It is
   unmeasured and would need kernel tracing.

## What this means now (Lexar in daily use, 924.6 GB free)

* Loading: ~60 MB/s sequential and ~0.8 ms per small random read. A faster SSD would not
  change this; the console sets the limit.
* Installs and other large writes: ~29 MB/s (inside write calls) for the first ~26 GiB after the
  console has idled, then ~12 MB/s. Deleting the 858 GiB filler freed filesystem space, but
  without TRIM the SSD probably still treats those blocks as in use, so expect the ~12 MB/s
  floor once a write runs past ~26 GiB. Most single game installs stay below that.
* None of this affects correctness or the M6 soak.

## Options, re-ranked against O01-O10

1. **Keep the stack as it is (O10). Recommended.** The read cap lives in LV1/LV2 storage code
   (high risk, no patch in this project), and the write cliffs are SSD-internal. No firmware
   performance work is justified.
2. **Offline TRIM of filesystem-free space from a PC (O09), only if large installs matter.**
   This is the only option aimed at the measured write floor. It needs:
   * an exact decode of the UFS2 free map (PS3HDDTool plus the console key) and the
     encrypted-partition LBA mapping;
   * a full drive image first, and owner approval naming the serial;
   * a before/after 40 GiB write test to show the gain.

   Large and risky: one wrong range destroys live data. Backlog.
3. **Request-size sweep (128/256/512 KiB), only if read speed matters.** It would confirm
   or refute the 64 KiB-chunk hypothesis using the RO1 framework, in one sitting. It is
   informational only, since any fix would mean patching LV1/LV2 storage handling.
4. **Retired:**
   * O01 and O03 are done by RO1/BH.
   * O02 and O04 only made the test apps faster.
   * O05 (allocator) is contradicted by point 3.
   * O06 and O08 have no measured target.
   * O07 is covered by the BF/BH comparison.
   * DR1 has no devices.
