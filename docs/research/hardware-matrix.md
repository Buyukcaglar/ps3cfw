## Actual Crucial sample probe

With explicit user authorization, the reviewed helper queried only the identified nonboot/nonsystem USB Disk3, rechecking size/model/bridge serial before every call. All three smartctl 7.5 SAT16 queries returned zero status: ATA identity, annotated IDENTIFY words and existing SMART health/capabilities/attributes/logs. The official release was extracted into the workspace; no installer/service was run. No disk initialization, format, data-sector write, setting or self-test command was issued.

Measured ATA identity is `CT2000BX500SSD1`, firmware `M6CR091`; serial stays in private local captures. Its reported capacity is **2,000,398,934,016 bytes**, **3,907,029,168 logical sectors**, with **512-byte logical and reported physical sectors**. Windows and ATA capacity agree. Word86 is `0x8401`, so bit10 is set; extended-capacity words100–103 are `88b0:e8e0:0000:0000`. These inputs are consistent with the traced LV1 extended-capacity path, but were not captured on the PS3 itself. P1's ceiling is 129,904,844,800 bytes higher.

SMART self-assessment passes; selected reallocation, pending, uncorrectable and CRC counters are zero. Its standard error log is reported unsupported, not a supported empty log; no self-tests are logged and none was started. Vendor raw counters require careful interpretation. Existing health indicators do not prove full media health or PS3 compatibility. See `observations/Crucial-PC-probe-summary.json`, `research/crucial-probe-review.md` and the retained original captures for exact values and limits.

The three manufacturer documents checked do **not** publish the actual ATA logical/physical sector geometry or LBA count for these samples. A 2TB label and SATA interface do not establish 512n versus 512e. PNY's datasheet wording about ECC bits per 2K sector describes error correction, and must not be interpreted as a 2048-byte ATA logical sector.

Lexar has older regional NQ100 documentation for **1920GB LNQ100X1920-RNNNU**. That is a distinct SKU from the user's current 2TB **LNQ100X002T-RNNNG**. Do not substitute the old capacity or its geometry in calculations. The current manufacturer's page data explicitly maps the new 2TB part even though some product illustration filenames still say 1920GB. [Older Lexar Americas page](https://americas.lexar.com/es/product/ssd-nq100/), [current global page data](https://www.lexar.com/global/_nuxt/static/1791455240/products/Lexar-NQ100-2-5%E2%80%9D-SATA-III-6Gb-s-SSD/payload.js).

## CECHA00 NAND and encryption family

Sony's public comparison page does not specify flash chips or HDD encryption. The maintained **PyPS3checker** source classifies CECHAxx/COK-001 models inside its `NAND` section, including separately listed refurbished models. Pinned source revision observed: `43d5f961708923ea547a1c69560741524415126d`; the NAND section starts at source line 8, the first CECHAxx/COK-001 SKU entry is line 607, and the NOR section begins at line 1613. This is primary developer tooling evidence for the CECHA00 family; it is not an inspection of this console. [PyPS3checker NAND mapping](https://github.com/littlebalup/PyPS3tools/blob/43d5f961708923ea547a1c69560741524415126d/PyPS3checker/checklist.xml#L607).

The PS3 HDD Reader implementation by 3141card/picard detects **FAT_NAND** using AES-CBC-192 and decrypts each sector independently with a reset IV. Its source tests the CBC partition-table result and distinguishes NAND versus NOR layouts, then dispatches the corresponding read path. This corroborates the CECHA family requirement to use the **FAT/NAND AES-CBC-192** recovery path rather than applying a Slim XTS-only recipe. Pinned inspected revision: `2e76371bd899f790fcc30ced163b9db62fb7671e`. [Detection and family selection](https://github.com/jhonathanc/PS3-HDD-Reader/blob/2e76371bd899f790fcc30ced163b9db62fb7671e/src/device.c#L104), [sector decryption](https://github.com/jhonathanc/PS3-HDD-Reader/blob/2e76371bd899f790fcc30ced163b9db62fb7671e/src/device.c#L239).

[PSDevWiki's original reverse-engineering notes](https://www.psdevwiki.com/ps3/HDD_Encryption) also identify NAND Phats as CBC-192 with a zero IV for each sector. [PS3HDDTool's author release](https://github.com/Pheeeeenom/PS3HDDTool/releases/tag/1.1) explicitly lists CECHA/B/C/E as FAT/NAND CBC-192 plus bswap16. The sources disagree about some **other Phat NOR** families; that disagreement does not affect the CECHA NAND intersection and should not be generalized into a recommendation for other models.

## Measurements needed before selecting a test SSD

Capture read-only identity information from each actual drive through direct SATA, if available, and retain the raw IDENTIFY data as well as the decoded result. Record full model/SKU, firmware revision, advertised byte capacity, logical sector size, reported physical sector size, logical sector count, sector alignment, and native versus currently exposed capacity. Keep the drive's serial in private local evidence if needed, rather than publishing it.

The primary smartmontools implementation derives capacity and logical/physical sector sizes from ATA IDENTIFY, then reports both sizes separately. Its `smartctl` manual documents read-only information output and annotated IDENTIFY output. Device paths must be selected after enumerating actual drives; no write, format, erase, HPA/DCO change, firmware update, or self-test is implied by this measurement step. [ATA size parsing](https://www.smartmontools.org/static/doxygen/atacmds_8cpp_source.html), [information reporting](https://www.smartmontools.org/static/doxygen/ataprint_8cpp_source.html), [official smartctl manual source](https://github.com/smartmontools/smartmontools/blob/main/src/smartctl.8.in).

An adapter may expose translated geometry rather than the SSD's native report. Compare any USB bridge result with direct SATA before drawing a 512n/512e conclusion. A reported 512/512 geometry is relevant to the PS3-visible interface; it does not prove the NAND flash internally writes in 512-byte units. The [PS3 512e investigation by andshrew](https://ps3hdd.pages.dev/blog/ps3-512e-compat/) independently documents PS3 filesystem metadata differences on an identified 512e drive, using a CECH-2503A and OFW 4.90. Treat those observations as a regression case to reproduce on CECHA00, not proof that every 512e device fails or every 512n device is safe.

For arithmetic only, exactly 2,000,000,000,000 bytes divided by 512 is 3,906,250,000 sectors, below 2^32. Commercial 2TB devices may expose a slightly different total; use each IDENTIFY count for bounds. This separates the decimal-2TB investigation from the 2TiB boundary, without claiming that 32-bit-safe arithmetic alone makes the console compatible.

All three SSDs are candidates for measurement, not qualified recommendations. Start the eventual firmware experiments with one identified, empty, healthy sacrificial drive, then repeat acceptance on the other actual SSD firmware/geometry combinations before claiming model coverage. A successful initial format, boot, or game launch does not establish full-capacity writes, repair/recovery behavior, or long-term data safety.
