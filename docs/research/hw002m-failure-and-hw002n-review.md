# HW002M result and HW002N review

12 October 2026. The user reported readiness, then a console copy-finished notification. The fixed HW002M tool received its large-copy response after 72.543 seconds and stopped on the exact size gate. It did not hash an assumed 8 GiB file or retry the copy. A separate read-only check found exactly 1,073,741,824 bytes. Its full native MD5 matches independently generated first-part bytes, whose SHA256 also matches the original USB receipt. The 16 MiB canary passed. All three full control hashes stayed unchanged. The user's subsequent all-green response affirms requested normal shutdown/restart/XMB/no repair prompt; no timing was supplied. Both actual files passed full native hash readback after that restart.

The earlier split-join review missed a concrete source defect. In the pinned webMAN `include/file/file_copy.h`, lines 284-290 decrement size to zero and then reduce chunk_size to zero. Lines 297-305 advance to the next split part with `goto merge_next`; the new part resets current_size/size but leaves chunk_size zero. Its next read therefore returns no data. This predicts a first-part-only output and agrees with the observed 1 GiB result. Installed binary/source equivalence remains unproven, so this is a strongly supported explanation rather than proof of the installed instruction sequence. It is not evidence of an 8 GiB firmware barrier.

HW002N avoids split-file joining. It uses two independent ordinary copy/append pairs in a new directory. A FAT32-safe 4 GiB minus 64 KiB body plus a 69,632-byte tail yields a fully populated 4 GiB plus 4 KiB file. The 16 MiB plus 4 KiB canary exercises the same append route first. Independent whole/segment manifests precede staging; exclusive USB writes and complete segment readback are required. Existing M/J files and F: firmware are untouched.

Pinned primary source remains webMAN commit d1d5b5271dc409677d101220e87024419fa59bcb. `cmd/write_trunc_unzip.h` parses the fixed `&b=` source first, then the filename's `&pos=`. Binary source size selects a 64/128 KiB allocation, `read_file` reads from offset zero, and the binary branch calls `write_file` with CREATE|WRONLY and no TRUNC or APPEND flag. `file/file.h` declares the destination offset u64, calls native cellFsLseek followed by cellFsWrite, and closes the descriptor. `init/eval.h` uses signed 64-bit _Stoll; these positive offsets fit. `ftp.h` stores REST in u64 and parses it with val. The fixed binary source paths fit the buffer; large tail is 69,632 bytes below 128 KiB. Small canary tail is 4096 bytes below 64 KiB. No binary payload text is interpreted as an offset because `&pos=` is supplied in the filename before `&b=`.

The append helper does not reliably check all seek/write/close results. Therefore exact body size before append, final size/full independently expected native MD5, exact high-offset tail and unchanged complete controls are acceptance requirements. A seek failure could affect only the new test file; no pre-existing destination is eligible. HTTP success is never treated as filesystem success.

The write command ends with http_response(CODE_PREVIEW_FILE). `www/www_client.h` defines this as 1225 and passes it into the HTTP response format in `init/html.h`. urllib refuses four-digit status codes. A dedicated socket reader is consequently restricted to the two fixed append endpoints and the fixed console IP; it sends once, accepts only exact documented 1225 or 200 status lines, bounds headers/body, rejects transfer encoding and inconsistent Content-Length, and follows no redirects. Its response is saved, then actual filesystem hashes determine success. Copy/hash requests retain the ordinary no-proxy/no-redirect client.

Native tool requires frozen bindings, full USB staging receipt and actual user readiness before creating a phase directory or connecting. Fixed FTP commands permit only source/destination sizes, root free space, one exclusive mkdir and a 4096-byte high-offset read. The after-boot phase permits no mkdir/copy/append. Durable intents precede requests; copy/append paths cannot repeat within a phase and phase directories cannot be reused. No deletion, rename, FTP upload, raw-device access, memory/syscall experiment, firmware change or repair command exists.

Host checks cover independent byte ranges around 2 GiB/4 GiB, contiguous body/tail arithmetic, native 64-bit size rejection, fixed command/peer restrictions, exclusive mkdir, read-only phase restrictions, fragmented high-offset read and fragmented/nonstandard HTTP responses. They do not establish PS3 execution. No stable, full-capacity, high-physical-address, durability or populated-repair claim is made.
